# SimpleLanguage 统一排查与语法规则（Front -> Export -> VM）

本文档是项目级排查与规则的**统一主文档**。  
原 `代码解析流程.md`、`语法规则.md` 已并入此文档，后续请只维护这里。

后续定位问题时，先按本流程检查；每次解决问题后，把方法补充到文末“复盘追加”。

**各文件含义与推荐阅读顺序（Logs / DebugCode / `*.module.json`）** 以 **`md/ai/DEBUG_WORKFLOW.md`** 为准（与 `EXPORT_PATHS.md` 中的路径约定一致）。

## 0) Front 代码解析总流程（由旧 `代码解析流程.md` 合并）

1. 汇总要编译的源文件列表。  
2. 对每个文件做 Token 化。  
3. Token 结构化为 Node（`[] { } ( ) < >` 等）。  
4. Node 归并到 FileMeta。  
5. 解析每个 FileMeta：
   - import / namespace
   - 类与层级关系（把 FileMeta 绑定到类的 variable/function）
   - 继承关系（先关系，后数据）
   - 成员变量与函数名称收集
   - 继承数据处理
   - 成员变量定义解析
   - 函数定义解析
   - 接口一致性检查
   - 成员表达式解析（拆解、优先级评估、排序后逐项解析）
   - 全局变量处理
   - 函数语句与返回变量解析并更新

> 上述流程的 Debug 对照见第 1 节（Core/Token/Node/File/Meta/IR）。

## 1) Front 编译链路（先看 DebugCode）

### 1.0) 固定文本日志 `Front.txt`（优先）

- 路径：加载 `jsonc` 后由 **`SIMPLELANG_LOGS_DIR`** 指向 **`{export.outputDir}/{export.moduleName}/Logs/`**，Front 日志文件名为 **`Front.txt`**。例如 Core：`E:\project\lang\simple_language\out\export\Core\Logs\Front.txt`（未加载配置时回退常量 `Log.FrontLogDefaultPath`）。
- 每次完整 Front 编译进入 `ProjectCompile.FileListStructParse` 时会**清空**该文件再写入本会话；排查当前编译问题应**先 Read 此文件**，再在 `DebugCode/` 里对照阶段输出。
- 日志行格式要点：`[Error] [ParseFile|ParseMeta|…] [LID名称] Position:[文件_行_列] Info:[…] Extend:[…]`。
- **DebugCode 文本**（`Code.txt` / `Token.txt` / …）：根目录为 **`{export.outputDir}/{export.moduleName}/DebugCode/`**（环境变量 **`SIMPLELANG_DEBUGCODE_ROOT`**）；其下再按源文件路径建子目录（与 `Common.GetDebugCodeDir` 行为一致）。`export.debugText` 中的 **`outputDir` 不再作为根路径**，仅保留各阶段开关。

- **从 Error 反推动作**：
  1. 用 `FileExpressFormatError` / `MetaCoreParseFileExpressFailed` 等 **LID** 在 `source/Front/Log/ErrorDefinitions.csv` 中查模板含义与 `paramCount`。
  2. 用 **Position** 中的路径与行号打开对应 `.sl` / `.sp` 源码；`Extend` 里常含当前词法片段，便于判断是词法（如 `>>` 被拆成两个 `>`）、表达式扁平化（如单独 `-1` 与前一操作数粘连）还是 Meta 阶段失败。
  3. 上游 File 层表达式未通过时，Meta 层的 `root is Null` 多为连锁反应，应先修 File 层再重编。

### 1.1) DebugCode 分层（按源文件一目录）

调试根目录为 **`{export.outputDir}/{moduleName}/DebugCode/`**（与 VM 包、`Logs` 同级）；**每个子目录对应一个被编译的源文件**（路径与 `.sl` 相对工程一致）。目录内常见文件：

- **`Code.txt`** — 该文件 **原始 `.sl` 源码** 快照（对照输入）。  
- **`Token.txt`** — 对 Code 的 **词法 / Token** 输出。  
  - 对应代码：`Compile/Parse/LexerParse.cs`  
- **`Node.txt`** — Token 的结构化整合：`()` `[]` `{}` `<>` 以及 **`.` 链式** 等；子元素与结构相关归并。  
  - 对应代码：`Node.cs` / `StructParseFrame.cs` / `StructParseToSyntax.cs`  
- **`File.txt`** — Node → **FileMeta / 文件级** 整合；语言阶段 **初步逻辑**，尚无完整 **实体语法**。  
  - 对应代码：`CompileFile` 相关流程  
- **`Meta.txt`** — **实体语法** 与 **语言逻辑关系**（MetaCore）。  
  - 对应代码：`source/Front/Core/*`  
- **`IR.txt`** — 将 Meta 侧语义整理为 **IR**，供导出读入并写入 **`*.module.json`**。  
  - 对应代码：`source/Front/IR/*`  

> 若工程历史中曾出现 `Core.txt` 等别名，以当前开关实际生成的 **`Code.txt`** 等文件名为准；语义层级与上表一致。

### Front 排查原则

1. 先看 **`Logs/Front.txt`**（完整路径见 1.0）中本会话最早一条 **Error** 及对应文件行；再检查最早出错阶段（Token/Node/File/Meta/IR）。  
2. 上游错误未修复前，不要直接在下游（VM）做补丁。  
3. 若 `IR.txt` 正确，再进入导出与 VM。

## 2) Export 导出检查（Front -> module.package.json）

当 `IR.txt` 正确后，检查导出 JSON 是否保持一致：

- 先看导出逻辑：`source/Front/Export/*`
- 重点文件：`source/Front/Export/SLIR/SLModulePackageWriter.cs`
- 默认导出路径（当前工程约定）：在 **`export.outputDir` 下再建一层 `export.moduleName` 目录**，例如：`out/export/Core/Core.module.json`（由 `SIMPLELANG_EXPORT_OUTDIR` 指向该模块目录）。

### 导出检查点

1. 类型/方法/字段数量是否与 `IR.txt` 对齐。  
2. 指令序列 `instructionList` 是否完整。  
3. `payload`（RuntimeDefType/RuntimeCall）是否与 IR 元数据匹配。  
4. `global.data`、array、data/object 初始化是否落入导出字段 `express`。

## 3) VM 运行链路（仅在 Export 正确后）

当导出正确时，再看 VM：

- 数据加载：`source/VM/Load/*`
- 解析与注册：`source/VM/Parse/*`
- 运行时执行：`source/VM/VMRuntime/*`

### VM 排查重点

1. 包加载与依赖顺序是否正确（module/entry）。  
2. RuntimeClass/RuntimeType 注册是否完整。  
3. `RuntimeVM.RunInstruction` 对应 opcode 处理是否存在缺口。  
4. 断言/错误日志对应的 RuntimeCall、RuntimeDefType 是否为空或映射失败。

### VM 运行结果镜像 `Result.txt`（print/println 输出）

- **路径**：与 **`VM.txt`** 同在 **`SIMPLELANG_LOGS_DIR`**（即 `…/export/<export.moduleName>/Logs/`）下，例如 `E:\project\lang\simple_language\out\export\Core\Logs\Result.txt`；未设置环境变量时回退 VM 工程 `Log.VmRunResultDefaultPath`。  
- **内容**：SL 侧 `global.print` / `global.println` 在控制台输出的**同一文本**会镜像追加到该文件（UTF-8）。  
- **启动提示**：VM 在打开该文件后会向控制台打印一行 **`[VMResult] OutputPath: ...`**，便于确认实际写入路径。  
- **覆盖目录**：若需改目录，设置环境变量 `SIMPLELANG_VM_RESULT_DIR` 指向目标**文件夹**（文件名仍为 `Result.txt`）。  
- **联合测试**：`dotnet run --project source/Test/SimpleLanguageTest.csproj` 走 in-process VM 时，同样会初始化/关闭镜像并写入上述路径（除非设置了 `SIMPLELANG_VM_RESULT_DIR`）。  
- **排查习惯**：对照 **`VM.txt`**（结构化日志）与 **`Result.txt`**（用户可见输出）可快速区分「运行时异常」与「业务打印是否符合预期」。

## 4) 标准排查顺序

### 4.1 运行时问题（「跑得对不对」）

1. **`Logs/Result.txt`** — VM 输出结果（`print`/`println` 镜像）。  
2. **`Logs/VM.txt`** — VM 运行时日志。  
3. **`*.module.json`** + 对应源文件在 **`DebugCode/`** 下的输出 — 核对指令与编译各阶段是否一致。  
4. 在某一文件的 DebugCode 目录内，通常按 **由深到浅反查**：**`IR.txt` → `Meta.txt` → `File.txt` → `Node.txt` → `Token.txt` → `Code.txt`**。

### 4.2 编译期问题（Front 报错、IR 以前失败）

1. **`Logs/Front.txt`** — 最早 **Error** 与阶段、行号。  
2. 同一文件 **`DebugCode/...`** 下按需在 **File / Node / Token / Code** 或继续 **Meta / IR** 对照。

### 4.3 导出与 VM 衔接

- **`IR.txt` 正确**后，再重点核对 **`*.module.json`** 与 VM 行为（`VM.txt` / `Result.txt`）。  
- 详细表格式说明见 **`md/ai/DEBUG_WORKFLOW.md`**。

## 5) 快速执行建议（CLI）

- Front 编译并导出 IR：`c -e ir -p <projectPath>`
- VM 执行：`dotnet run --project source/VM/SimpleLanuageVM.csproj -- <module.package.json>`
- 联合测试（推荐）：`dotnet run --project source/Test/SimpleLanguageTest.csproj -- <projectPath>`

### [2026-09-11] JsonTest asMap containsKey/取值失败：比较函数缺少 Object 槽标量包装归一化（移植 C# NormalizeObjectReferenceKindInPlace）
- 现象：新增 JsonTest 中 `asMap containsKey`、`asMap 取值` FAIL；map 插桩日志显示 hashId 命中（ent_hash==want）但 `runtime_value_compare_equal` 对 key 返回 false。
- 首个异常阶段：VM（runtime_value_compare_equal 字符串分支）。
- 根因：MapEntity.key 经成员读取得 `etype=EVMType_String`，栈上弹出的字符串 key 经 `vm_try_pop_runtime_value` 得 `etype=EVMType_Object`（vm_object 指向 String 包装）。字符串比较分支要求双边 String 才 strcmp，一边 Object 即 equals=FALSE，随后 fall through 到引用比较（两个不同 String 对象指针不等）。C# VM 在比较前有 `TryNormalizeObjectScalarInPlace` + `NormalizeObjectReferenceKindInPlace`（Object 槽装标量包装时采用包装真实 etype），C VM 缺此步骤。
- 修复点（文件/模块）：`csimple_lang/src/vm/runtime/runtime_value/runtime_value_compare.c`——新增 `vm_cmp_normalize_object_reference_kind_in_place` 并在 `runtime_value_compare_equal` 开头对 a/b 调用；String 包装仅原地改 etype（包装 member[0] 存裸 char*，`vm_object_new_string`，不能走 `vm_object_try_load_member_value` 解包，与 vm_runtime.c Switch 解包 `!= EVMType_String` 排除一致）；其他标量包装（Int32/Float64…）整体替换为 `vm_object_try_load_member_value(obj,0)` 读出的值（等价 C# SetValueBySObject）。
- 如何快速复现：JsonTest 的 `user.asMap()` 后 `containsKey("name")` / `m["name"].asString()=="alice"`。
- 如何快速验证：`dotnet run --project project\CSimpleVMStdTest -- -p test\JsonTest\JsonTest.sp -test` 全绿（含 asMap 三断言）。
- 预防建议：C VM 比较语义与 C# 基准逐分支对照（`source/VM_extracted/.../RuntimeValueCompare.cs`）；凡"类型相同值相同却比较失败"，先怀疑 etype 不一致（成员读出 vs 栈弹出路径的 etype 约定不同），用插桩打两边 etype 取证；该归一化同时修复所有「Object 槽标量包装 vs 直接值」比较场景。

### [2026-09-11] JsonTest 嵌套 float 取值失败：非 bug——无后缀小数字面量默认 Float32 的精度语义
- 现象：`user["height"].asFloat64() == 1.68` FAIL，而同形式 `nums[2].asFloat64() == 4.5` OK。
- 首个异常阶段：非 VM 缺陷（词法语义 + 精度）。
- 根因：无后缀小数字面量默认 Float32（`LexerParseToToken.cs` EndReadNumberByOtherChar，注释"无后缀的小数字面量（含 0.0）默认 float32"）。module.json 中 1.68 常量 payload 4 字节 `3D 0A D7 3F` = Float32(1.68)≈1.6800000667572021，而 asFloat64 用 strtod 得 Float64 1.68≈1.6799999999999999；C# 基准（RuntimeValueCompare.cs TryCompareNumericValue）同样把 Float32 提升为 double 后比较，C# VM 下此断言也 FAIL。4.5 二进制精确（100.1₂），Float32 无损所以碰巧通过。
- 修复点：无代码修复；测试断言改为 `1.68d`（Float64 字面量）并补 `asFloat32() == 1.68f` 覆盖 Float32 路径（test/JsonTest/JsonTest.sl）。
- 如何快速复现：任一 SL 工程写 `X.asFloat64() == 1.68`（1.68 换任意二进制不精确小数）。
- 如何快速验证：JsonTest 全绿；Grep module.json 确认常量 byteLength=4（Float32）vs `1.68d` 为 8 字节。
- 预防建议：比较 Float64 返回值一律用 `d` 后缀字面量（Float32 用 `f`）；无后缀小数按 Float32 理解，勿与 C/C#/Java 的 double 默认混淆。

- 修复引入的回归（本条核心教训）：第一版把 `sys_throw_epoch` 插进 `SLVmExtVm` **镜像前缀中部**（error_code/execute_index 之间）→ 平移其后所有镜像字段偏移 → 未重编的旧插件 DLL（echo、csharp_mono）按**旧偏移**错位读取镜像字段（症状：Echo(3.5) 出 Assert、testIntRoundtrip error_code=-91 提前停止）。取证：插件 DLL（09-23/09-24）与 csimple_lang_dll.dll 时间戳对比确认二进制 ABI 失配。二次修复：字段挪到镜像前缀**之后**的 VM 专属区（stack_slot_depth 后）+ 撤销 sl_vm_ext_api.h 镜像改动，镜像前缀恢复原始布局，旧插件无需重编。
- 如何快速验证：重建 Debug 后沙盒宿主 `passed=16 failed=0`、testDegradation 五项全 PASS（含 after-catch 栈清洁 Add(2,3)==5）、VM.txt 中 `CallSystemMethod failed` 与 `[Assert]` 均 0 条、F5 不再弹断点中断框。
- 预防建议：① 判定「系统方法意外失败」不能只看 error_code——凡存在同步 throw 路径（vm_sys_throw 等），必须区分「失败」与「已派发并被 catch 的业务异常」（时序快照/epoch 类手段）；② **SLVmExtVm 镜像前缀（止于 stack_slot_depth）冻结**：编译期被外部插件 DLL 固化偏移，中部插字段=全体旧插件错位失效；VM 新字段一律放镜像之后的 VM 专属区（约定已写入 vm_runtime.h 注释）；③ 排障期间引入的 stderr 直写插桩（OOMTRACE/BOOT 等）闭环后必须全量清理（本次 48 处），否则污染正常输出且日后误导排障；④「测试异常流中断」与「测试断言失败中断」都表现为 __debugbreak，先看 stderr/logs 分辨是哪条 Assert 路径，别急着怀疑异常派发本身。

### [2026-09-24] @csharp_mono 协程+isolate 示例 20 全绿后退出阶段 0xC0000005：isolate 三段式根因——shell 反向引用过早清空 / 跨线程分配域不对称 / 主 shell 在 vm_destroy 前被释放致 TLS 悬垂
- 现象：SpecialTest 新增 testAtSignCoro（协程 spawn+await 调 mono）/testAtSignIsolate（Isolate.run 在另一线程执行 mono 并返回结果）后全部 20 用例 PASS 全绿，但进程退出阶段崩溃 0xC0000005——「测试全绿 + 退出崩溃」，退出码非 0。
- 排查路径：R12 先插桩（SLCS_TRACE 门控 stderr，Start-Process OS 级重定向落盘，逐层加桩逐层跑）→ trace 停在 VD5：`run_vm_with_module → vm_isolate_shutdown() → vm_destroy → VD5 vm_free_object_pool → obj[0] vm_array_free → vm_mem_sba_free → vm_mem_sba_current`；结合崩溃偏移符号化 + 读源码确认 sba 路由链 `TLS→iso→iso->vm→vm->mem_manager->sba` 中 iso 悬垂、iso->vm 读出 -1、按 (VM*)(-1) 解引用 mem_manager 即 AV。三段式：每修一层重跑取证，暴露下一层。
- 根因（三段叠加，按发现顺序）：
  ① shell 反向引用过早清空：主 isolate shell 的 iso->vm 在 VD5 之前被清，VD5 池对象释放经 shell 路由取不到 vm → 修复①：反向引用清除块移到 VD6 之后（vm_runtime.c post-VD6 块）。
  ② 跨线程分配域不对称：worker 线程在主 VM 分配域 carve 的池对象，释放时按释放线程路由错 sba 域 → 修复②：vm_memory.h/c 新增 vm_mem_alloc_domain_set per-thread 分配域 override；vm_isolate_reap 内 set/restore 域重定向；isolate_system_method.c launch_common 显式 domain_set(NULL)。
  ③ 主 shell 在 vm_destroy 前被释放致 TLS 悬垂（本崩溃直接根因）：vm_isolate_shutdown 在 vm_destroy 之前把主 shell 一并 base_free，但主线程 TLS 仍指向它；随后 vm_destroy 的 VD5/VD6 池释放经 TLS 拿到悬垂 shell → 修复③：shutdown 循环改断链遍历，主 shell（is_main）摘除保留（s_main_isolate 继续指向）；新增 vm_isolate_release_main() 由 CLI 在 vm_destroy 之后调用（释放 shell 字段+本体，最后清主线程 TLS）。worker 路径不变：thread_main 尾部自 reap（毁 worker VM、shell 保留）→ 清自己线程 TLS → shutdown 循环释放 worker shell。
- 关键设计约束（为何不能简单清 TLS=NULL）：主 VM 的池对象 carve 在主 VM 自己的 mem_manager->sba，VD5/VD6 释放依赖 `TLS→iso→iso->vm→mem_manager->sba` 路由；TLS 先清 NULL 会错路由到进程静态 s_main_sba → 堆损坏（历史上冻结 bug 的镜像）。主 shell 必须活到 vm_destroy VD6 之后——「路由载体必须活过依赖该路由的最后一次释放」。
- 修复点（文件/模块）：vm_runtime.c（post-VD6 反向引用清除块）；vm_memory.h/c（per-thread 分配域 override）；vm_isolate.c（reap 域重定向 / shutdown 断链+主 shell 保留 / vm_isolate_release_main 新增）；vm_isolate.h（声明）；isolate_system_method.c（launch_common domain_set(NULL)）；cli_command.c（vm_destroy 后调 vm_isolate_release_main）。排障插桩 7 文件 77 处调用已全量清理，重建零 error 零 warning。
- 如何快速复现（修复前）：`csimple_lang.exe run <SpecialTest.module.json>`（含 isolate/协程用例）→ 20 [PASS] 全绿打印完后退出阶段 AV 0xC0000005。

- 预防建议：① shutdown/destroy 序列要区分「VM 所有权」与「shell 所有权」：凡带线程本地路由（sba 按线程域路由）的资源，载体生命周期必须覆盖依赖该路由的最后一次释放，先用后松；② 「对象本体释放」与「线程绑定（TLS）清除」必须同点成对出现，只做一半 = 悬垂或错路由二选一；③ 头插链表 shutdown 优先断链逐个摘除而非边遍历边释放再置全局头，主/特殊节点（is_main）显式豁免并交由所有者释放；④ 全绿≠收工：退出码必须纳入验收（Start-Process -PassThru 查 .ExitCode），「测试断言 + 进程退出码」双指标。
